# Multi_AgentDecisionCouncil

Multi_AgentDecisionCouncil 是一个面向复杂议题分析、方案推演与架构脑爆的多智能体决策工作台。系统把一次讨论拆成“人类发题 + 多 Agent 串行分析 + 会话级总结沉淀”的闭环，适合创业推演、产品战略、技术方案评审、风险审计和执行路线设计。

## 项目目标

这个项目不是通用聊天框，而是一个有编排逻辑的决策控制台。用户先给出一个问题、机会、方案或文档背景，然后由多个角色不同的 Agent 从不同视角接力分析。每一轮输出不只是回答问题，还会把结果沉淀到长期摘要中，下一轮继续在已有上下文上推进，而不是每次从零开始。

## 整体架构

系统采用前后端分离架构：

- 前端：`Vue 3 + Vite`
  - 负责侧栏配置、主时间线展示、底部输入区、主题切换、文件挂载与导出入口
- 后端：`FastAPI`
  - 负责模型探测、会话生命周期、文件解析、流式事件推送、存档和导出
- 编排层：`graph.py + agents.py`
  - 负责多 Agent 的顺序执行、消息组装、总结模型调用和导出内容生成
- 技能层：`skill_registry.py + skills/`
  - 负责 Agent 人设 / 提示词配置的版本管理与装配
- 公共能力层：`hub/`
  - 放置配置、模型辅助逻辑和数据结构

## 目录结构

- `backend/api.py`
  - API 入口，提供 bootstrap、模型探测、会话执行、文件解析、导出与会话存档接口
- `frontend/src/components/`
  - `SidebarPanel.vue`：会话、模型、Agent 编排和存档入口
  - `ChatTimeline.vue`：主讨论时间线
  - `ComposerDock.vue`：底部输入与文件 / 干预 / 导出入口
- `agents.py`
  - Agent 规格、提示词装配、流式回复和导出逻辑
- `graph.py`
  - 决策轮次的执行图
- `skills/`
  - 内置提示词人设版本
- `sessions/`
  - 会话存档目录

## 决策脑爆逻辑

当前默认是 3 个 Agent：

1. `Agent A`
   - 偏商业战略、机会判断、价值路径和优先级
2. `Agent B`
   - 偏反向质询、架构可行性、技术约束和方案拆解
3. `Agent C`
   - 偏执行顾问、风险控制、落地路径和失败预案

每个 Agent 都可以单独配置：

- 是否启用
- 使用的模型
- 提示词人设
- 局部附加提示词

### 一轮讨论的执行方式

一轮不是多人并发乱聊，而是一个有顺序的决策回路：

1. 用户输入一个议题
2. 系统读取当前启用的 Agent 列表、模型配置、提示词人设和上传资料
3. Agent A 先输出自己的分析
4. Agent B 读取用户问题和前面已产生的上下文，继续输出
5. Agent C 再基于同一轮材料和前面 Agent 的内容给出补充与审视
6. 本轮结束后，总结模型更新长期摘要
7. 用户再基于本轮结果继续追问，进入下一轮

所以“几人几轮”的关系是：

- 几人：默认 3 人，可按轮次启用或关闭
- 几轮：不固定，由用户持续推进
- 每轮结构：`1 次人类输入 + N 个已启用 Agent 串行输出 + 1 次摘要更新`

### 人机交互方式

每轮的人机交互是单入口、多反馈：

- 人类只需要在底部输入区发出一个议题或追问
- 系统会把这次输入作为当前轮的唯一人类指令
- 每个 Agent 的输出会实时流式写入主时间线
- 如果某个 Agent 还未开始，会显示等待状态
- 如果执行失败，会在该 Agent 卡片下显示中断原因
- 当全部 Agent 结束后，会话摘要会更新到顶部摘要区

这使得整个交互模式更像“主持一场结构化脑暴”，而不是普通对话。

## 上下文与记忆机制

系统的上下文由三部分组成：

- 当前轮用户输入
- 历史轮次消息
- 会话级长期摘要

其中长期摘要不是简单复制聊天记录，而是压缩后的高价值记忆。这样做的目标是：

- 让多轮讨论能保留主线
- 避免上下文无限膨胀
- 让后续轮次更快进入高信息密度分析

## 文件挂载机制

用户可以上传资料作为讨论背景，支持：

- `txt`
- `md`
- `pdf`
- `docx`
- `csv`
- `json`
- `yaml / yml`

后端会先解析文本，再把文件内容作为上下文材料拼接到本轮输入环境中。适合用于：

- PRD
- 商业计划草稿
- 会议纪要
- 技术方案
- 表格型约束信息

## 模型与提示词人设

每个 Agent 有两层配置：

- 模型：决定推理能力、成本和风格
- 提示词人设：决定角色视角与输出取向

这两层分离的意义是：

- 同一个人设可以挂在不同模型上
- 同一个模型可以承担不同角色
- 角色设计与模型选型可以独立迭代

此外还有一个独立的总结模型，用于维护长期摘要和导出内容。

## 会话与导出

系统支持：

- 新建会话
- 保存会话
- 读取历史会话
- 导出 Markdown
- 导出 Mermaid 图内容

会话的核心数据包括：

- 项目名称
- 历史轮次
- 当前摘要
- 上传资料

因此一个会话不是一次性结果，而是一个可连续推进的决策工作流。

## 启动方式

### 后端

```bash
./start_api.sh
```

默认监听：

- `http://127.0.0.1:8000`

### 前端

```bash
./start_frontend.sh
```

默认监听：

- `http://127.0.0.1:5173`

### 本地一键脚本

本地可以保留单终端启动 / 停止脚本：

- `launch_terminal_start.sh`
- `launch_terminal_stop.sh`

这两个脚本用于本机工作流，不作为仓库发布内容的一部分。

## 环境要求

- Python 3.11
- Node.js 18+
- npm 9+

## 安装

### Python 依赖

```bash
pip install -r requirements.txt
```

### 前端依赖

```bash
cd frontend
npm install
```

复制配置模板：

```bash
cp .env.example .env
```

常用变量：

- `SHARED_DEEPSEEK_API_KEY`
- `ARK_API_KEY`
- `AGENT_A_MODEL`
- `AGENT_B_MODEL`
- `AGENT_C_MODEL`
- `SUMMARY_MODEL`

```bash
cd frontend
npm run build
```
